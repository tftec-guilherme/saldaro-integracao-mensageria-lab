Ver a Saldaro funcionando

A jornada de uma fatura, à mão, no Portal: você faz o papel do ERP (~10 min)

1

Mande uma fatura pela aba Test do APIM

API saldaro → POST /faturas → Test, com o header x-cliente-id: cliente-a; volta 201 Created com o faturaId

2

Acompanhe o status pelo GET /faturas/{id}

cobranca-emitida → registrada → baixada → notificada, em menos de um minuto

3

Veja as filas no Service Bus

sbq-confirmacoes-banco e sbq-notificacoes-parceiro: a mensagem entra e sai; sbq-faturas-recebidas fica parada

4

Veja as tabelas no Storage browser

faturas: status, idCobranca e quantidadeBaixas; cobrancas: uma cobrança só para a fatura

5

Veja a jornada no Application Insights

Investigate → Search pelo faturaId, entre aspas; o End-to-end mostra a parte síncrona

Integração e Mensageria no Azure — um dia de incidente na Saldaro

13

Tempo previsto: 10 min. Mostrar no Portal: apim-saldaro-(sufixo) → APIs → saldaro → POST /faturas → Test; o GET /faturas/{id}; sb-saldaro-(sufixo) → Overview e Entities → Queues; stsaldaro(sufixo) → Storage browser → Tables; appi-saldaro-(sufixo) → Investigate → Search e Application map. Cuidados de telão. Ao abrir Logs, use o KQL mode e desligue o Agent. Em Environment variables, use Show value só na linha, para não expor os outros valores na tela. O smoke test prova a jornada por script. Agora a gente faz a mesma jornada à mão, sem script nenhum, e eu faço o papel do ERP. Na aba Test da operação POST /faturas, adiciono o header x-cliente-id com o valor cliente-a; sem ele, o hub responde 400. No Request body, em Raw, vai uma fatura com valor, vencimento e referenciaErp DEMO-001. Send: volta 201 Created com o faturaId, o status cobranca-emitida e o idCobranca. Reparem: no baseline, o POST é síncrono. O hub chamou o banco simulado dentro da requisição e só respondeu quando o banco devolveu a cobrança. É essa herança que o Incidente 1 conserta. Agora o GET /faturas/{id}, repetido a cada poucos segundos. cobranca-emitida: o hub gravou a fatura e o banco registrou a cobrança. registrada: o banco mandou o webhook cobranca.registrada, assinado, pela API saldaro-webhooks, e o hub enfileirou na sbq-confirmacoes-banco. baixada: veio o cobranca.paga, o worker fez a baixa e publicou o FaturaBaixada no Event Grid. notificada: o Event Grid entregou na sbq-notificacoes-parceiro e o hub avisou o ERP. Tudo em menos de um minuto. No Service Bus, as duas confirmações entraram e saíram da sbq-confirmacoes-banco: o Active volta a 0, mas cliquem em Refresh, porque a página não se atualiza sozinha. A sbq-faturas-recebidas está parada; quem passa a usar essa fila é o conserto do Incidente 1. No Storage browser, a tabela faturas tem a linha com status, idCobranca e quantidadeBaixas, e a cobrancas tem uma cobrança só. A prova do Incidente 1 é exatamente essa contagem. No Application Insights, esperem de 2 a 5 minutos de ingestão. Em Search, o faturaId entre aspas traz a jornada inteira, de fatura.recebida a fatura.baixada. Abram o POST: o End-to-end transaction details mostra só a parte síncrona, APIM, hub e banco simulado, porque o webhook sai de uma fila de Storage e o Event Grid inicia operações novas, com outro operation_Id. Não é erro: o faturaId é a correlação de negócio, e é ele que prova a jornada. Por fim, o Application map: é a arquitetura do slide "O que vamos montar", viva, com chamadas e latência em cada seta. Reparem no que mais é ingênuo de propósito: a connection string é a RootManageSharedAccessKey, a fila de confirmações não tem sessions nem duplicate detection, e não existe alerta nenhum. Pergunta para a turma: olhando essa jornada, qual peça vocês acham que vai nos trair primeiro? Se perguntarem "notificação a qual parceiro?": aqui, "parceiro" é o termo guarda-chuva para banco parceiro e ERP, e a notificação vai sempre ao ERP da empresa cliente, pelo callbackUrl da fatura, nunca ao banco. Transição: sexta-feira, 18h. O banco entrou em manutenção.
